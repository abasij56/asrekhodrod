# ایده: نوبت‌دهی مجازی برای خرید / ثبت‌نام (مثل نوبت بانک)

> **فقط یادداشت ایده** — دستورالعمل اجرا، پرامپت، یا الزام پروژه نیست.  
> برای نگه داشتن بحث تا فراموش نشود. مدل نهایی هنوز قطعی نیست.

تاریخ ثبت: ۱۴۰۴/۰۵/۰۷ (2026-07-29)

---

## زمینه

سایت فعلی عصر خودرو بیشتر خبری/محتوایی است (WordPress).  
اگر بخواهد برای خرید درست شود و همزمان حدود **۱۰۰ هزار نفر** هجوم بیاورند، مدل احتمالی یکی از این دو است:

1. **ثبت‌نام طرح خودرو**
2. **محصول فیزیکی محدود**

مشکل اصلی معمولاً خود صفحه نیست؛ بلکه **موجودی/سهمیه، پرداخت، و دیتابیس** در لحظه اوج است.  
WordPress معمولی برای این سناریو کافی نیست؛ مسیر خرید باید از سایت خبری جدا باشد.

---

## ایده اصلی: نوبت بانکی

مثل بانک:

1. هر کس نوبت می‌گیرد و منتظر می‌ماند
2. بر اساس نوبت صدا زده می‌شود
3. کارش را انجام می‌دهد
4. نفر بعدی فراخوانی می‌شود

نسخه وب:

1. افراد نوبت می‌گیرند
2. به آن‌ها **شماره نوبت + کد پیگیری** داده می‌شود
3. وقتی نوبتشان شد، مثلاً SMS می‌رود: «نوبت شماست؛ روی لینک کلیک کنید»
4. با کلیک وارد سایت می‌شوند و بقیه مراحل (فرم / احراز / پرداخت) را انجام می‌دهند
5. چون ممکن است عده‌ای انصراف دهند یا تایم‌اوت شوند، بعد از صف اصلی یک **صف رزرو (waitlist)** هم هست؛ نفر اول رزرو جایگزین می‌شود

این الگو همان Waiting Room / Virtual Queue است و برای هر دو مدل بالا منطقی است.

---

## چرا جواب می‌دهد؟

- فشار همزمان شکسته می‌شود
- فقط تعداد محدودی همزمان وارد مرحله حساس خرید/ثبت می‌شوند
- موجودی/سهمیه کنترل‌پذیر می‌ماند
- حس عدالت («نوبت من مشخص است») بهتر از کرش یا خطای تصادفی است

---

## نسخه بالغ‌تر ایده (نه لزوماً یکی‌یکی)

در بانک یک باجه دارید؛ اینجا سرور می‌تواند چند نفر را همزمان بپذیرد.

پیشنهاد عملی:

- **Batch admission:** هر ۳۰–۶۰ ثانیه مثلاً ۵۰ نفر بعدی باز شوند  
  یا همیشه حداکثر مثلاً ۱۰۰ نفر «در حال خرید» فعال باشند
- به محض اتمام / انقضا / انصراف، نفر بعدی از صف بیاید
- لینک فراخوانی **زمان‌دار و یک‌بارمصرف** باشد (مثلاً ۵–۱۰ دقیقه)
- وضعیت زنده داخل سایت مهم‌تر از تکیه صرف به SMS است (SMS ممکن است دیر برسد)

---

## فلو پیشنهادی

```text
Landing (ویترین / CDN)
  → گرفتن نوبت (سبک، عمدتاً Redis)
  → صف اصلی یا صف رزرو
  → فراخوانی (SMS + وضعیت پنل)
  → پنجره اقدام (فرم / شرایط / پرداخت)
  → رزرو موقت موجودی (TTL)
  → تأیید نهایی
  → در صورت انصراف/انقضا: نفر اول waitlist صدا زده شود
```

### وضعیت‌های پیشنهادی تیکت

- `queued` — در صف اصلی
- `waitlisted` — در صف رزرو
- `called` — نوبتش شده، اطلاع ارسال شده
- `in_progress` — وارد لینک شده، در حال تکمیل
- `reserved` — موجودی/سهمیه موقت رزرو شده
- `confirmed` — ثبت/پرداخت نهایی موفق
- `expired` — زمانش تمام شد
- `cancelled` — انصراف
- `promoted` — از رزرو به فراخوانی آمده

### قانون صف رزرو (نمونه)

1. ظرفیت اصلی مثلاً ۱۰۰۰
2. صف رزرو مثلاً ۳۰۰۰ نفر بعدی
3. اگر `confirmed` به سقف برسد → تمام
4. اگر کسی `expired/cancelled` شود و ظرفیت خالی بماند → نفر اول `waitlisted` فراخوانی شود
5. قوانین از قبل شفاف اعلام شود (فرصت مجدد؟ یا انتهای waitlist؟)

## مشترکات زیرساختی (مستقل از مدل نهایی)

- جدا کردن سرویس سفارش/ثبت‌نام از WordPress خبری
- کش/CDN برای محتوا؛ مسیر خرید کنترل‌شده
- صف پردازش (Queue) به‌جای هجوم مستقیم به DB
- موجودی/سهمیه atomic (Redis یا `UPDATE ... WHERE stock > 0`)
- رزرو موقت با TTL
- Idempotency برای پرداخت / webhook
- Rate limit و ضدبات
- Load test قبل از روز اوج
- مانیتورینگ: latency، error rate، طول صف، DB lock

هسته مشترک پیشنهادی تا قطعی شدن مدل:

- Campaign / Offer (طرح یا محصول با ظرفیت)
- Quota / Stock engine
- Participant (محدودیت یکتا: کد ملی یا user+sku)
- Order / Registration با وضعیت‌های بالا
- Payment adapter (ودیعه یا پرداخت کامل)
- Eligibility rules (برای طرح خودرو پیچیده‌تر)

## تفاوت دو مدل محتمل

| موضوع | طرح خودرو | محصول فیزیکی محدود |
|--------|-----------|---------------------|
| موجودی | سهمیه / ظرفیت طرح | موجودی انبار |
| هویت | خیلی حیاتی (کد ملی) | مهم، معمولاً ساده‌تر |
| قوانین | پیچیده (واجد شرایط بودن) | ساده‌تر |
| پرداخت | ممکن است ودیعه/ثبت‌نام باشد | معمولاً کامل |
| بعد از خرید | تخصیص / پیگیری طرح | ارسال کالا |
| ریسک اصلی | ثبت تکراری + بی‌عدالتی صف | oversell + پرداخت دوبل |

اگر مدل «همه ثبت‌نام کنند، بعد قرعه» باشد، فشار بیشتر روی ثبت‌نام مقیاس‌پذیر است تا موجودی لحظه‌ای.  
اگر «هر کس زودتر رسید سهمیه گرفت» باشد، نوبت‌دهی مجازی خیلی مهم‌تر است.

---

## ریسک‌ها و راه‌حل‌ها

| ریسک | راه‌حل |
|------|--------|
| SMS دیر برسد | وضعیت زنده در سایت + SMS؛ تایمر شفاف |
| کاربر بیاید ولی نخرد | رزرو موقت با TTL کوتاه |
| فروش/واگذاری نوبت | تیکت متصل به هویت؛ غیرقابل انتقال |
| ربات نوبت جمع کند | Captcha + احراز زودهنگام |
| همه همزمان روی لینک بزنند | فقط N نفر active؛ بقیه locked |
| کاربر آنلاین نباشد | چند تلاش محدود + قانون شفاف انتقال به رزرو |
| حس بی‌عدالتی | قوانین از قبل اعلام‌شده + لاگ حسابرسی |

گلوگاه احتمالی در مقیاس بالا: SMS provider و درگاه پرداخت، نه خود ایده نوبت.

---

## سؤالات باز (برای قطعی کردن معماری)

1. همه ثبت‌نام می‌کنند بعد قرعه، یا هر کس زودتر رسید سهمیه می‌گیرد؟
2. پرداخت آنلاین در همان لحظه لازم است یا فقط ثبت‌نام؟
3. محدودیت یکتا روی کد ملی است؟
4. ظرفیت تقریبی چقدر است نسبت به متقاضی؟
5. یک کمپین اوج است یا فروش مداوم؟

---

## جمع‌بندی یک خطی

ایده «نوبت بانکی + کد پیگیری + فراخوانی با لینک + صف رزرو برای انصراف» برای این سناریو درست و عملی است؛ نسخه بالغ‌اش با فراخوانی گروهی محدود، تایم‌اوت سخت، اتصال به هویت، و سرویس جدا از WordPress باید دیده شود.
